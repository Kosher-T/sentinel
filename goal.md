# Sentinel: Production Architecture & Deployment Guide

## 1. Overview
Sentinel is an autonomous, production-ready MLOps agent designed to safeguard the performance and integrity of deployed AI models. Operating alongside your primary application, Sentinel provides continuous monitoring, statistical drift detection, automated alert escalation, and closed-loop model retraining capabilities.

It ensures that AI systems in production remain reliable over time, automatically intervening when data drift or model decay is detected.

## 2. The Core Philosophy: "Sidecar Agent"
Sentinel is built on a **Sidecar Architecture**. It is not a monolithic platform that hosts your models. Instead, it is a lightweight, decoupled agent designed to run adjacent to your existing ML inference endpoints. 

This approach guarantees:
* **Zero Latency Impact:** Sentinel's operations (watching, extracting, analyzing) run asynchronously and do not block or slow down your main application's inference requests.
* **Agnostic Integration:** Sentinel monitors the inputs and outputs (the "exhaust") of your model, making it largely agnostic to the specific framework (PyTorch, TensorFlow, Scikit-learn) running the inference.

## 3. Deployment Environments
Sentinel is designed to be highly versatile and can be deployed wherever your model resides:

### A. Local / On-Premise Deployments
For models deployed on local hardware, edge devices, or internal enterprise servers, Sentinel runs as a Docker container on the same host machine. It connects to the host's local storage volumes to monitor input/output directories and log files in real-time.

### B. Cloud Virtual Machines (IaaS)
For models hosted on cloud infrastructure (e.g., AWS EC2, GCP Compute Engine, Azure VMs), Sentinel should be deployed as a companion container on the same VM instances serving the traffic. A lightweight VM (e.g., t2.micro or e2-micro) is sufficient to handle Sentinel's overhead, as intensive analysis is scheduled and batched.

### C. Container Orchestration (Kubernetes)
In Kubernetes environments, Sentinel is deployed as a literal "sidecar container" within the same Pod as your primary inference container. They share a mounted volume where the inference container writes its logs and data, which Sentinel continuously monitors.

## 4. Primary Use Cases
Sentinel is optimized for scenarios where model reliability is mission-critical and manual monitoring is unscalable:

* **Continuous Model Performance Monitoring:** Ensuring that the predictions generated by a production model do not degrade over time compared to a curated "Golden Set" of baseline data.
* **Automated Data Drift Detection:** Identifying when the distribution of incoming live data shifts significantly away from the data the model was originally trained on.
* **Intelligent Data Curation (Smart Distillation):** Automatically filtering massive volumes of production data to curate high-value, hard-to-predict examples for future retraining, minimizing storage costs and optimizing training time.
* **Closed-Loop Retraining Orchestration:** Autonomously triggering CI/CD pipelines to provision compute, retrain the model on fresh data, evaluate the new "Challenger" model against the current "Champion," and deploy the update if performance is improved.

## 5. High-Level Architecture Components

### A. The Monitored Environment (Your Application)
* **The Primary ML Endpoint:** The service receiving requests, generating predictions, and saving the input/output pairs (or logging them) to a designated location.

### B. Sentinel Core (The Sidecar Container)
* **Sentinel Watcher (`sentinel_watch.py`):** A lightweight daemon that continuously monitors designated directories or streams for new inference data.
* **Data Extractor:** Securely pulls recent inference data batches for analysis.
* **Drift & Decay Detectors:** * *Data Drift Analyzer:* Calculates statistical confidence intervals to compare live input distributions against the established baseline.
    * *Model Decay Analyzer:* Evaluates the quality of model outputs against the expected performance thresholds defined by the Golden Set.
* **System State Tracker:** Maintains the operational status and historical context of the monitoring loop.

### C. Cloud Storage & State Management
* **Object Storage (AWS S3 / GCP Cloud Storage):**
    * Securely stores **Golden Sets** (curated, high-quality reference datasets used as the ultimate source of truth).
    * Archives historical inference data and distilled datasets (`data_rotator` / `distiller`).
* **Model Registry (`model_registry.py`):** The centralized ledger tracking the active "Champion" model version, historical versions, and evaluating incoming "Challenger" models.

### D. Automated Orchestration & CI/CD
* **Validation Workflows:** Scheduled or manually triggered GitHub Actions (or equivalent CI/CD platforms) to run deep, intensive statistical validation checks without taxing the production host.
* **Retraining Pipeline:** An automated workflow triggered via secure webhooks when Sentinel confidently confirms severe model decay. It handles compute provisioning, model training, and initiates the Challenger evaluation.

### E. Human-in-the-Loop Operations
* **Command Center Dashboard:** A Streamlit-powered UI providing real-time visualization of drift metrics, confidence intervals, system state, root cause analysis, and model registry status.
* **Alert Escalation (`alert_escalation.py`):** A dispatch system routing critical alerts and retraining notifications to engineering teams via Slack, Email, or custom webhooks.
